# Vira Reader migration

The project repository is now [Ares-X/Vira-Reader](https://github.com/Ares-X/Vira-Reader), retaining repository ID 1394160942 and its Git/issue/PR history. This is a branding preview; no Vira Reader version has been publicly released. Public downloads remain Sumra 0.2.47. New source builds produce `Vira Reader.app`; Swift targets and the internal executable remain Sumra.

The icon follows the maintainer's supplied monochrome double-page V reference. [Icon sources and generation prompts](../Assets/AppIcon/README.md) describe the light/dark PNG inputs; the normal build makes all ten ICNS sizes. The four README variants use the new brand banner and distinguish unreleased source builds from the existing public download.

The application uses `dev.aresx.vira-reader`, with `.preview` and `.thumbnail` extensions. Existing exported document UTIs and the `sumra://synctex` integration remain compatible. The Ares-X signing certificate and Sparkle Ed25519 key are unchanged. Existing diagnostic/cache storage remains in its current location. A one-time preference migration reads the old `dev.aresx.leaf` domain, preserves existing new-domain choices, copies settings/history/bookmarks/positions without changing the old domain, and excludes old Sparkle delivery/runtime state. It runs before diagnostics and language initialization. Native macOS saved windows and default file-handler selection are separate OS state and are not claimed to migrate.

Changing both the application filename and bundle ID means stock Sumra 0.2.47 cannot identify the new bundle as an in-place update. The first transition requires manually installing `Vira Reader.app`. The old `appcast.xml` remains frozen for Sumra; the new identity uses `vira-appcast.xml`, initially a valid empty feed because this round does not publish a Vira Reader version. Future Vira releases update only the new feed. No custom installer, bridge build or duplicate update archive is introduced. Signed manual installation and preference migration passed in the existing macOS 26.6.2 VM; details follow below.

At the maintainer's explicit selection, 77 older releases and their 461 assets were deleted, representing 14,224,912,496 logical bytes. Public versions 0.2.45/46/47 and the previously accepted 0.2.48 draft were retained with their original asset identities. All 48 Git tag refs and commit history remained unchanged. The separately built new-identity candidate passed the acceptance recorded below. No billing or physical storage reclamation is inferred from asset sizes.

After repository rename, the old and new raw feeds returned identical bytes, all 18 preserved old asset URLs were reachable, the three public checksum manifests matched, and old/new Git HEADs matched. The old PR URL redirected correctly. The old issue #158 webpage initially returned 404 even with a unique query. A later bare GET at 2026-11-17 09:45:39 UTC returned 200 and redirected to the canonical new issue URL; the initial failure and recovery evidence are retained. Both API paths always returned the same issue ID. No reporter reply was posted.

Evidence is retained under `build/issues-remaining48/rebrand/`: exact cleanup manifests and per-release deletion receipts, post-rename public compatibility probes, packaging/localization checks, and focused native tests. The original bug-fix draft's signed acceptance is recorded separately in [the issue acceptance record](ISSUES_158_160_161_ACCEPTANCE.md).
